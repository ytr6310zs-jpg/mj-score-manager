# UX 実践チェックリスト（一般プラクティス準拠）

**目的**: 画面・操作が一般的な Web アプリの慣例から外れていないかを、出典付きで確認しやすくする。  
**正本の置き方**: 一般プラクティスの詳細は外部（Nielsen / WCAG 等）を正とし、本ファイルは **観点・検証手順・リポでの見方** のみを持つ。長い独自ガイドラインを増やさない。  
**リポ固有 ADR**: `design/adr/` は例外・上書きがあるときだけ参照する（例: 遷移中フィードバックは ADR 0009 / 0019）。  
**親 Issue**: [#304](https://github.com/ytr6310zs-jpg/mj-score-manager/issues/304)  
**カタログ**: `.specify/specs/issue-304-ux-audit-and-fixes/ux-findings.md`

## 使い方

1. 洗い出し・PR レビュー・エージェント操作確認では、下表を上から見る。
2. 不合格は findings に ID を付け、既存 Issue へ振るか新規 Issue 化する。
3. 「リポ流だから正しい」ではなく、まず一般慣例で判定する。ADR と衝突するときだけ ADR を読む。
4. a11y の機械ゲート（`eslint-plugin-jsx-a11y` / axe 等）は本リストを代替しない。補完として使う。

## 出典（参照のみ・全文転載しない）

| 略号 | 出典 |
|---|---|
| N1–N10 | Nielsen Norman Group, 10 Usability Heuristics |

## チェック項目

| ID | 観点 | 出典 | 合格の目安 | このアプリでの見方 |
|---|---|---|---|---|
| G01 | 操作結果のフィードバックは一度・一箇所 | N1, FORM | 成功／失敗が利用者に伝わり、同じ成功を二重に出さない | `FlashMessage`（`?flash=`）またはフォーム内 Alert のどちらか。**遷移型なら遷移先 flash のみ**（編集画面に成功文を出してから自動遷移しない） |
| G02 | 待ち・進行中が分かる | N1, WCAG | 送信・プレビュー・エクスポート中に disabled／文言／`aria-busy` 等 | 取り込みプレビュー、編集送信、CSV/PDF、ヘッダー遷移（ADR 0019） |
| G03 | エラーはエラーに見える | N1, N9 | 成功色・成功アイコンでエラーを出さない。回復の手がかりがある | `flash-message` の種別、フォーム Alert、日付不正 |
| G04 | 権限・拒否は黙って戻さない | N1, N9 | 拒否時に理由（flash／バナー／専用文）がある | import／admin／edit の redirect、middleware |
| G05 | 空状態と「条件で 0 件」を混同しない | N1, N6 | データ無しとフィルタ結果 0 件で文言・CTA が違う | `/stats`・`/compatibility`・サブ表 |
| G06 | 推奨導線と deprecate が矛盾しない | N4, NAV | 主 CTA・空状態・ナビが現行の推奨登録経路と一致 | #305: 取り込み優先。`/` は非推奨（積極 UX 改修対象外） |
| G07 | ユーザーの明示操作が押し戻されない | N3, N7 | フィルタ「条件なし」等の選択が勝手に戻らない | `FilterStateSync` / 共有フィルタ / `minGames` |
| G08 | ナビ・戻る先が予測できる | N3, NAV | キャンセル／戻るが `history.back` 任せで迷子にならない | 編集キャンセル、パンくず相当の「履歴へ」 |
| G09 | 破壊的操作に確認がある | N3, N5 | 削除前に確認。可能なら文脈付きのインページ確認 | 対局／ユーザー／大会／役満削除 |
| G10 | 二重送信・連打で壊れない | FORM | 送信中は再送できない。ナビ連打で状態が壊れない | `pending`／`disabled`。ロックしすぎて操作不能に感じないこと（#333） |
| G11 | ラベル・名前・状態が支援技術に伝わる | WCAG | 入力に accessible name。非表示 DOM が二重に読まれない | スコアスピンボタン、レスポンシブ二重 DOM、チェックボックス |
| G12 | ページの識別ができる | WCAG, NAV | 主要画面に適切な `document title` / metadata | login／admin 配下など |
| G13 | システム状態と実データが矛盾して見えない | N1, N2 | 「データが無い」と言いながら他画面では一覧がある、等を避ける | 履歴あり × 成績 0 件（フィルタ説明不足） |
| G14 | エラーページ・未知 URL の最低限 | NAV, FORM | 予期せぬエラー／404 で白紙やスタックだけにならない | `error.tsx` / `not-found.tsx`（App Router） |
| G15 | 認証フォームがブラウザ慣例に沿う | FORM, WCAG | パスワードマネージャ向け `autocomplete` 等 | `/login` の userId / password / otp |

### スコープ外（本リストで意図的に扱わない）

- `/` スコア入力 UI の見た目・UX 改善提案（#305 / project-core）
- 集計アルゴリズム性能（#130）、印刷レイアウト本体（#268 側）、schema／RLS 変更

## ミューテーション後フィードバック（G01 詳細）

どちらか一方を選ぶ。混在禁止。

| 型 | いつ使うか | 成功時 |
|---|---|---|
| **遷移型** | 編集完了後に一覧へ戻すなど | 元画面に成功 Alert を出さない。遷移先で flash のみ |
| **滞在型** | 連続登録・取り込み確定後も同画面で続ける | 同画面に成功を出し、**自動遷移しない**。必要なら「一覧へ」リンク |

現状のリポ慣例: 対局編集・削除は遷移型（`?flash=updated|deleted`）。admin のインライン CRUD は滞在型（`router.refresh`）。取り込み確定は滞在型。

## エージェント／レビュー用の最短手順

1. 対象画面で主要操作（表示・フィルタ・送信・権限差・キャンセル）を一度通す。
2. 上表 G01–G15 を該当するものだけ合否記録する。
3. 不合格は `ux-findings.md` に追記し、サブ Issue 化または既存 Issue へリンクする。
4. サブ Issue 本文に、違反した **Gxx** を書く（一般プラクティス根拠を残す）。
