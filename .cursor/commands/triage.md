# Triage Issue（変更クラス判定）

Issue 着手時に **変更クラス（A–D）** を判定し、必須承認点を提示してユーザー合意を取ります。  
マトリクス正本: `docs/issue-prompt-guidelines.md`（Issue #308）。

実装・コミット・push・PR 作成はしないでください。

## `/clarify` との違い

| コマンド | 役割 |
|---|---|
| `/triage` | 変更クラス判定・必須承認点・ユーザー合意（本コマンド） |
| `/clarify` | 要件の不明点洗い出し（クラス合意の正本ではない） |

設計承認スキップ（A/B）は **本コマンド（または委任文面）でクラス合意済み** のときだけ適用する。未合意のままスキップしてはならない。

## 手順

1. ユーザーが指定した Issue 番号（なければ確認する）を対象にする
2. GitHub MCP（または `gh issue view`）で `ytr6310zs-jpg/mj-score-manager` の Issue と本文・コメントを取得する
3. 想定差分から変更クラスを判定する（自信がなければ **fail-up**）
4. 次を提示して **ユーザー合意を待つ**（合意前に `/design` の承認スキップや `/implement` に進まない）:

### 出力テンプレート

```text
## Triage 結果（案）

- Issue: #<番号> <タイトル>
- 推奨クラス: A | B | C | D
- 根拠: <想定タッチファイル／リスクの要約>
- fail-up したか: いいえ / はい（理由）

### 必須承認点（このクラス）

| 項目 | 扱い |
|---|---|
| 設計承認（設計完了停止） | スキップ可 / 必須 / 必須＋影響明示 |
| Spec | PR Spec 可 / 薄い3点推奨 / 3点必須 |
| commit / push / `/pr` | 明示依頼（クラス不問） |
| `/release`（PROD） | 常に人間承認（クラス不問・代替不可） |

### 次のアクション

- クラスに合意する場合: 「クラス <X> で合意」と返信（必要なら修正クラスを指定）
- 不明点が多い場合: `/clarify` を先に実行してよい（その後あらためてクラス合意）
```

5. ユーザーがクラスを合意（または修正指定）したら、以降の `/design` / `/implement` はそのクラスのルールに従う。合意クラスと根拠を以降の出力冒頭で再掲する

## 判定の目安（要約）

- **A**: 文書・設定・コメント・commands のみ
- **B**: UI 文言・表示条件・テスト追加など低リスク実装
- **C**: 画面ロジック・集計など通常機能
- **D**: schema / 認証 / RLS / 破壊的変更（影響範囲の明示必須）

`supabase/migrations` や認証・認可コードを含む見込みがあれば C 以上、破壊的・権限変更なら **D**。

## 制約

- コード変更・コミット・push・PR 作成はしない
- `/release` や main 反映をトリアージ合意で代替しない
- `/design` の main↔develop 同期ゲート・hooks / worklog / `npm run build` は緩和しない
- 参照: `docs/issue-prompt-guidelines.md`, `AGENTS.md`, `.cursor/commands/design.md`
