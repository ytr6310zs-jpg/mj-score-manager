# Feature Specification: 画面全般の UI/UX 問題検出・修正（親）

**Feature Branch**: `feature/issue-304-ux-audit-and-fixes`  
**Created**: 2026-11-20  
**Status**: Approved — 実装中  
**Related Issue**: [#304](https://github.com/ytr6310zs-jpg/mj-score-manager/issues/304)  
**Change class**: **C**（トリアージ合意済み 2026-11-20）  
**Input**: 急ごしらえ由来で一般的な Web アプリと乖離する挙動を検出し、適切な修正で UI/UX を改善する。親 Issue として改修はサブ Issue に分ける。

---

## 背景・目的

アプリは対局記録・成績・管理の実用に足るが、遷移・空状態・フォーカス・権限別 CTA・モバイル導線などが慣例から外れている箇所がある。Issue #304 はそれらを洗い出し、優先度付きで直すための **親 Issue** である。

既に完了したサブ: [#310](https://github.com/ytr6310zs-jpg/mj-score-manager/issues/310)（ヘッダー／E2E 遷移契約）。#305 により `/` スコア入力は deprecate（積極メンテ対象外）。ログイン後着地は `/matches`。

本親 Issue の成果は「巨大な一括 UX リライト」ではなく:

1. **検出カタログ**（画面・観点・深刻度・既存 Issue への振分）
2. **サブ Issue の切り出しとトリアージ**
3. **優先サブの実装完了**（または明示的な見送り）により親をクローズできる状態にする

### 確定方針（設計案）

| ID | 決定 |
|----|------|
| Q1 | 親は検出・優先付け・サブ管理のハブ。**修正実装は原則サブ Issue**（各サブで `/triage`） |
| Q2 | 既存オープン Issue と重複する指摘は新規サブを作らず **既存へリンク**（#268 印刷表、#261 edit URL、#31 ページネーション 等） |
| Q3 | deprecate の `/` スコア入力は **積極改修対象外**（致命的なブロッカーのみ例外。原則 #305 方針維持） |
| Q4 | schema / 認証・認可モデル変更は本親のスコープ外（必要なら別 Issue・クラス D） |
| Q5 | 親の完了条件は「カタログ確定＋P1 サブがクローズ（または見送り合意）＋残サブが Issue 化済み」 |

## User Scenarios & Testing *(mandatory)*

### User Story 1 - UX 乖離の検出カタログを作る (Priority: P1)

メンテナとして、主要画面を決められた観点で見て、一般 Web 慣例からの乖離を一覧化し、深刻度と既存 Issue 振分を残したい。

**Why this priority**: 以降のサブ切り出しと優先度の正本になる。

**Independent Test**: リポジトリ内のカタログ（例: `.specify/specs/issue-304-ux-audit-and-fixes/ux-findings.md` または同等）を見て、画面×観点の行があり、未振分の「要サブ Issue」が判別できる。

**Acceptance Scenarios**:

1. **Given** 対象画面一覧（下表）, **When** 検出を実施する, **Then** 各画面について観点チェック結果がカタログに残る（問題なしも記録可）
2. **Given** 検出項目, **When** 既存 Issue と重複する, **Then** 新規サブを増やさず既存番号へリンクする
3. **Given** deprecate の `/`, **When** 検出する, **Then** 致命的でない項目は「対象外（#305）」と分類する

**対象画面（初回パス）**

| パス | 備考 |
|---|---|
| `/login` | 認証入口 |
| `/matches` | 主着地・一覧 |
| `/matches/import` | 主登録経路 |
| `/matches/.../edit` | 修正経路（URL は #261 と関連） |
| `/stats`・印刷系 | 閲覧・FB |
| `/admin` 配下 | 権限付き |
| `/` | deprecate。致命的のみ |

**検出観点**

正本: [`docs/ux-practice-checklist.md`](../../../docs/ux-practice-checklist.md)（一般プラクティス G01–G15）。要約のみ:

- 操作結果フィードバックは一度・一箇所（遷移型／滞在型を混在させない）
- 空状態・エラー・権限不足時の文言と CTA
- フォーカス／キーボード／モバイルの主要操作
- ナビゲーション一貫性（ヘッダー・戻り・現在地）
- 破壊的操作の確認
- ローディング・二重送信の防止
- a11y の明らかな破綻（ラベルなしボタン、誤った role 等）— #310 済み領域は回帰確認のみ
- document title、error/not-found、認証フォーム慣例

### User Story 2 - 優先度付きサブ Issue を切る (Priority: P1)

メンテナとして、カタログの要対応項目をサブ Issue（または既存 Issue への割当）にし、各サブで変更クラスをトリアージできるようにしたい。

**Why this priority**: 親を巨大 PR にしない前提の実行単位。

**Independent Test**: GitHub 上に親 #304 を参照するサブ（またはリンク付き既存 Issue）があり、P1/P2 が分かる。

**Acceptance Scenarios**:

1. **Given** カタログの「要サブ」項目, **When** 切り出す, **Then** 各サブに目的・受け入れ・非スコープ・親 #304 が書かれる
2. **Given** サブ着手前, **When** `/triage` する, **Then** クラス A–D が個別合意される（親 C をサブに自動転用しない）
3. **Given** #268 / #261 / #31 等, **When** 内容が一致する, **Then** 重複サブを作らない

---

### User Story 3 - P1 修正を完了し親をクローズ可能にする (Priority: P2)

メンテナとして、検出で P1 とした乖離をサブ経由で直し（または見送り合意し）、#304 を完了扱いにできる状態にしたい。

**Why this priority**: Issue タイトルの「修正」に対応。実装本体はサブ。

**Independent Test**: P1 サブがすべて closed（完了または won't fix 合意）し、カタログの P1 が解消または見送り済み。

**Acceptance Scenarios**:

1. **Given** P1 サブ, **When** 実装・マージする, **Then** カタログ上の該当行が「対応済み」になる
2. **Given** P1 を見送りる判断, **When** Issue／カタログに理由を残す, **Then** 親完了条件の「見送り合意」を満たす
3. **Given** P2 以降が残る, **When** 親をクローズする, **Then** 残件はオープン Issue として追跡され、親本文またはカタログから辿れる

---

### Edge Cases

- 検出で schema／認可モデル変更が必要 → 本親では直さず別 Issue（想定クラス D）
- サブが #268 等の大規模機能と一体化 → 機能 Issue 側で完了し、カタログはリンクのみ
- 印刷レイアウト改善は #268 に寄せ、本親の「見た目の微修正」と混同しない
- 成績速度（#130）・バックアップ（#109）・CI Actions（#246）は UX 検出の対象外

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST（プロセス）初回パス対象画面について検出カタログをリポジトリに残す
- **FR-002**: System MUST（プロセス）各検出項目に深刻度（P1/P2/P3 または同等）と振分先（サブ／既存／対象外）を付ける
- **FR-003**: System MUST NOT 親 #304 単一 PR で無関係な全画面リライトを行う
- **FR-004**: System MUST 重複する既存 Issue へ振分け、重複サブを作らない
- **FR-005**: System MUST deprecate `/` の非致命項目を積極改修対象外とする
- **FR-006**: System MUST P1 対応（完了または見送り合意）後に親クローズ条件を満たしたとみなせる
- **FR-007**: サブの実装 MUST 各サブのトリアージクラスと Spec ルールに従う

### Key Entities

- **Finding**: 画面、観点、現象、期待、深刻度、振分先、状態
- **Sub-issue**: 親 #304 を参照する GitHub Issue（または既存 Issue へのリンク）

---

## Success Criteria *(mandatory)*

- **SC-001**: 初回パス対象画面の検出カタログが存在する
- **SC-002**: 要対応 P1 がすべてサブ化または既存 Issue 振分済み
- **SC-003**: P1 が完了または見送り合意され、親 #304 をクローズできる
- **SC-004**: schema／認証モデル変更が本親の実装差分に混入していない

---

## Assumptions

- 検出はメンテナ／エージェントのレビューと必要なら手動操作で行い、専用監査ツールの新規導入は必須としない
- #310 で直したヘッダー／E2E 契約は「済み」とし、回帰が出た場合のみ再オープンまたは新規サブ
- クラス C は親の設計・ハブ作業に適用。サブは個別トリアージ

---

## 非スコープ

- `/` スコア入力の機能拡充・専用 E2E 復活（#305）
- #268 / #261 / #31 / #130 / #109 / #246 の本親への吸収実装（リンクのみ）
- デザインシステム全面刷新、ブランドビジュアルの作り直し
- Prisma 移行・大規模リファクタ
