# Feature Specification: 集計ルール変更（2027-01 以降適用）

**Feature Branch**: `cursor/issue-292-scoring-rules-2027-b7b7`  
**Created**: 2026-11-18  
**Status**: Approved — 実装中  
**Related Issue**: [#292](https://github.com/ytr6310zs-jpg/mj-score-manager/issues/292)

---

## 背景・目的

現行は「25,000点持ち / 30,000点返し、ウマなし」の最終スコアを **整数（千点単位）** で `games.score1`–`score4`（INTEGER）に保存する。順位はスコア降順から導出し、成績の `totalScore` はその合計である。

Issue #292 の要求:

1. 小数第1位まで記録可能にする
2. Mリーグ風の順位点（ウマ）を運用に含める
3. Mリーグルール準拠候補の採用／見送りを整理する
4. **2026年の集計には新ルールを適用しない**（適用開始日による切替）

### 確定方針（2026-11-18）

| ID | 決定 |
|----|------|
| Q1 | **A** — ウマ込みの最終ポイントを既存どおり `score*` に入力。アプリはウマを自動加算しない。**ガイド UI は作らない** |
| Q2 | **A** — 本 Issue の採用範囲は **適用日切替 + 小数第1位 + ウマ運用（入力規約）** |
| Q3 | **A** — 3人打ちは新ルール日でも **ウマなし**（小数のみ）。4人打ちのみウマ運用 |

---

## User Scenarios & Testing *(mandatory)*

### User Story 1 - 適用日によるルール切替 (Priority: P1)

運営者として、対局日が適用開始日より前の対局は現行ルールのまま扱い、適用開始日以降だけ新ルールで検証したい。2026年の通期集計が新ルールで汚染されないことを保証したい。

**Why this priority**: Issue が「今年中の集計では適用してはいけない」と明示。他要件の前提。

**Independent Test**: 適用開始日前後の対局を登録し、バリデーション（整数のみ vs 小数可、許容誤差）が切り替わることを確認できる。

**Acceptance Scenarios**:

1. **Given** 適用開始日が `2027-01-01`, **When** `date < 2027-01-01` の対局を登録する, **Then** 現行ルール（整数・ウマなし・許容 ±1）で検証される
2. **Given** 同上, **When** `date >= 2027-01-01` の対局を登録する, **Then** 新ルール（小数第1位可・新許容）で検証される
3. **Given** 2026年の対局のみを集計対象にした成績画面, **When** 集計する, **Then** 新ルール由来の再計算・補正が混入しない
4. **Given** 開発・検証目的, **When** 適用開始日を上書きする手段がある, **Then** 本番既定を変えずに新ルールを試せる

---

### User Story 2 - 小数第1位のスコア記録 (Priority: P1)

記録者として、新ルール適用日以降の対局では最終スコアを小数第1位まで入力・保存・表示したい。

**Why this priority**: Issue の明示要件。

**Independent Test**: 新ルール日に `12.5` などを登録し、履歴・成績・エクスポートで精度が残る。旧ルール日は非整数を拒否する。

**Acceptance Scenarios**:

1. **Given** 新ルール適用日の対局, **When** 小数第1位のスコアを入力する, **Then** 保存・再表示で同じ値になる
2. **Given** 旧ルール適用日の対局, **When** 非整数を入力する, **Then** 拒否される
3. **Given** 新ルールで合計が 0（新許容内）, **When** 登録する, **Then** 成功する
4. **Given** スプレッドシート取り込み, **When** 新ルール日の小数スコアを含む行を取り込む, **Then** 不要な `Math.round` で小数が消えない

---

### User Story 3 - 順位点（ウマ）付きスコア運用 (Priority: P2)

記録者として、新ルール適用日以降の4人打ちでは、ウマ込みの最終ポイントを既存のスコア欄に入力して登録したい。アプリによるウマ自動加算やガイド表示は不要。

**Why this priority**: 運用規約の変更。入力 UI の追加は最小（ガイドなし）。

**Independent Test**: ドキュメント／仕様上「新ルール日の 4p はウマ込み最終ポイントを入力」と一貫し、保存・集計は入力値のままである。

**Acceptance Scenarios**:

1. **Given** 新ルール日の 4人打ち, **When** ウマ込み最終ポイントを `score*` に入力して登録する, **Then** その値が保存され成績合計に使われる（自動加算なし）
2. **Given** 旧ルール日の対局, **When** 登録する, **Then** 従来どおりウマなし前提の最終ポイント入力
3. **Given** 新ルール日の 3人打ち, **When** 登録する, **Then** 小数は許可され、ウマ運用は求めない
4. **Given** スコア入力画面, **When** 表示する, **Then** ウマ表ガイドや自動ウマ UI は出ない

---

### User Story 4 - Mリーグルール候補の整理 (Priority: P3)

運営者として、Mリーグ準拠候補の採用／見送りが一覧され、実装スコープが限定されていることを確認したい。

**Independent Test**: 仕様の採用表を見て、実装タスクに曖昧な項目が残っていない。

**Acceptance Scenarios**:

1. **Given** Mリーグで一般に言及される項目, **When** 設計を読む, **Then** 採用・見送り・ドキュメントのみに分類されている
2. **Given** 見送り項目, **When** 実装する, **Then** 本 Issue のスコープに含めない

---

### Edge Cases

- 適用開始日ちょうど（`2027-01-01`）は新ルール
- 新旧対局が混在する集計は、各対局の **保存済みスコアをそのまま合算**（再計算しない）
- 同点時の順位は現行どおり（スロット順で一意化）。同着ウマ分割は導入しない
- 既存 INTEGER データの型変更後も旧値が正確に読めること
- 手動入力と取り込みの合計 0 許容を RuleSet で揃えること

## Requirements *(mandatory)*

### Functional Requirements

- **FR-001**: System MUST 対局日に基づきスコア検証ルール版を選択できる（既定適用開始日: `2027-01-01`）
- **FR-002**: System MUST 適用開始日より前の対局に現行ルール（整数・ウマなし・合計許容 ±1）を維持する
- **FR-003**: System MUST 適用開始日以降、スコアを小数第1位まで受け付け・永続化・再表示できる
- **FR-004**: System MUST 新ルール用の合計 0 許容誤差を定義し、手動入力と取り込みで揃える（推奨: `0.1`）
- **FR-005**: System MUST 4人打ちのウマ運用を「入力者がウマ込み最終ポイントを入れる」規約としてドキュメント化する（自動加算しない）
- **FR-006**: System MUST NOT ウマ表ガイド UI やウマ自動加算 UI を追加する
- **FR-007**: System MUST 3人打ちについて、新ルール日でもウマ運用を要求しない（小数のみ）
- **FR-008**: System MUST 成績・履歴・エクスポートが、新ルール経路で保存済み小数精度を落とさない
- **FR-009**: System MUST ローカル検証用に適用開始日の上書き手段を提供する（未設定時は `2027-01-01`）
- **FR-010**: System MUST NOT 2026年対局の保存済みスコアを一括で新ルールへ再計算・上書きする

### Key Entities

- **ScoringRuleSet**: ルール版、適用開始日、スコア精度、合計許容誤差
- **GameScore**: 対局1名分の最終ポイント（ウマ込みか否かはルール日と game_type の運用規約。保存は単一値）
- **Game (既存)**: `date` がルール選択キー

---

## Success Criteria *(mandatory)*

- **SC-001**: `date < 適用開始日` の対局を現行整数ルールで登録でき、回帰テストが通る
- **SC-002**: `date >= 適用開始日` で小数第1位が保存・再表示され、読取後も精度が失われない
- **SC-003**: 2026年範囲のみの成績集計が、本機能導入前後で（同一データなら）一致する
- **SC-004**: 新ルール日の 4p はウマ込み入力規約、3p は小数のみ、のいずれもガイド UI なしで登録できる
- **SC-005**: Mリーグ候補の採用／見送り表が仕様にあり、実装が採用項目に閉じている

---

## Assumptions

- 保存単位は「最終ポイント（千点スケール）」。持ち点（25000 等）は DB に持たない
- 4p ウマの参考値は **+30 / +10 / −10 / −30**（入力者の計算用。アプリは検証に使わない）
- 飛び・飛ばし・焼き鳥・役満は本 Issue で変更しない
- 順位（`rank*`）は引き続きスコア降順から導出
- 管理画面のルールエディタは作らない
